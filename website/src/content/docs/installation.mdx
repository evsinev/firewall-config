## Prerequisites

| | |
|---|---|
| **Java 8** | The project compiles with `source`/`target` `1.8`. It runs on newer JREs, but do not raise the compiler level without checking — see [Limitations](/firewall-config/internals/limitations/). |
| **Maven** | Not needed separately; use the bundled `./mvnw` wrapper (Maven 3.5.2). |
| **`nwdiag`** | Only to render the [L3 diagram](/firewall-config/generators/l3-diagram/) to PNG/SVG. The generator itself only writes `network.diag`. Install with `apt install python3-nwdiag` (the binary is then `nwdiag3`). |
| **A desktop session** | Only for the interactive [L2 editor](/firewall-config/generators/l2-diagram/). The SVG and PNG variants run headless. |

Dependencies resolve from Maven Central plus `https://maven.pne.io`, which is declared in `pom.xml`
and publicly readable.

## Download

Every release attaches the ready-to-run fat jar as `firewall-config-<version>.jar`. Pick one from
the [releases page](https://github.com/evsinev/firewall-config/releases), or with the GitHub CLI:

```sh
gh release download --repo evsinev/firewall-config --pattern 'firewall-config-*.jar'
mv firewall-config-*.jar firewall-config.jar     # the name every wrapper script expects
```

What changed in each release is in
[`CHANGELOG.md`](https://github.com/evsinev/firewall-config/blob/master/CHANGELOG.md).

## Build

<Steps>

1. Build the fat jar — the assembly is bound to the `package` phase, so nothing else is needed:

   ```sh
   ./mvnw clean package
   ```

2. Two jars land in `target/`. The one you want is the shaded one:

   ```
   target/firewall-config.jar        # ~6 MB, everything included, runnable
   target/config-1.1-SNAPSHOT.jar    # classes only, not runnable
   ```

3. Check it runs:

   ```sh
   cd examples/demo-network && mkdir -p gen
   java -jar ../../target/firewall-config.jar . group-internal gen
   ```

</Steps>

The `1.1-SNAPSHOT` in the thin jar's name is the version that has been in `pom.xml` since 2013 and
means nothing — release versions come from the git tag.

## How it is released

Pushing a semver tag is the whole release process:

```sh
git tag -a 1.2.0 -m "1.2.0" && git push origin 1.2.0
```

[`.github/workflows/release.yml`](https://github.com/evsinev/firewall-config/blob/master/.github/workflows/release.yml)
then stamps the tag as the project version, builds the fat jar, regenerates the demo network as a
gate, and publishes a GitHub release whose notes are the matching `CHANGELOG.md` section — a
missing section fails the build, which is what keeps the changelog honest.

The jar being downloadable does not change how it is *used*. The convention is still that **each
network description repository carries the jar it was generated with**, copied in as
`firewall-config.jar` next to a few shell wrappers:

```
firewall-<site>/            # the network description repo
├── hosts/ protocols.yml networks.yml …
├── firewall-config.jar     # copied from target/, committed
├── firewall-config.sh
├── firewall-l3.sh
└── firewall-l2-svg.sh
```

This makes every generated rule set reproducible from that repository alone, at the cost of
committing a binary. Upgrading the tool is a deliberate act: rebuild, copy the jar in, re-run
everything, and review the diff of the generated output.

Typical wrappers:

## Running it in CI

The description repository is the natural place for the pipeline: on every push, regenerate
everything and fail if a generator rejects the configuration. A JDK 8 image with `nwdiag`
pre-installed (for example `payneteasy/jdk-8-nwdiag:2`) covers all of it.

```yaml title=".gitlab-ci.yml in the description repo"
test:
  image: payneteasy/jdk-8-nwdiag:2
  script:
    - mkdir -p target gen
    - ./firewall-config.sh
    - ./firewall-l3.sh
    - ./firewall-l2-svg.sh
```

Because most misconfigurations are hard errors rather than warnings — an unknown protocol, a subnet
missing from `networks.yml`, a `vip` with no VRRP peer, a NAT direction that cannot be resolved —
this doubles as validation of the description itself.
